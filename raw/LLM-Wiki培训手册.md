## 一、什么是 LLM Wiki

### 1.1 核心理念

传统的 RAG（检索增强生成）方式是：每次提问时，AI 从原始文档中检索片段，拼凑回答。知识每次从零发现，不会积累。

LLM Wiki 的做法完全不同：

| | 传统 RAG | LLM Wiki |
|---|---|---|
| **知识处理** | 每次查询时临时检索 | AI **预先**将知识编译成结构化 Wiki |
| **积累性** | 无积累，问完即忘 | 知识**持续积累**，交叉引用已建好 |
| **维护者** | 无 | AI 自动维护所有页面和引用 |
| **产出物** | 仅聊天回答 | 一套持久的、可浏览的 Markdown 知识库 |

**一句话总结**：你负责选择源文件和提出问题，AI 负责摘要、交叉引用、索引维护和一致性检查。Wiki 是一个**持续复利的知识资产**。

### 1.2 三层架构

```
┌─────────────────────────────────────────────┐
│  Schema（模式/规范）                          │
│  .github/copilot-instructions.md            │
│  告诉 AI：角色、格式、流程、领域约定            │
├─────────────────────────────────────────────┤
│  Wiki（知识层）                               │
│  wiki/ 目录下的所有 Markdown 页面              │
│  AI 全权负责写入和维护                         │
├─────────────────────────────────────────────┤
│  Raw（原始源）                                │
│  raw/ 目录下的源文档                           │
│  不可修改的事实来源                             │
└─────────────────────────────────────────────┘
```

### 1.3 三大操作

| 操作 | 触发方式 | AI 做什么 |
|------|----------|-----------|
| **摄入（Ingest）** | "请摄入 raw/xxx.md" | 创建摘要页 → 更新概念/实体页 → 更新索引和日志 |
| **查询（Query）** | 直接提问 | 读索引 → 定位页面 → 综合回答 → 可存为专题页 |
| **维护（Lint）** | "请 lint 一下 Wiki" | 检查矛盾、孤立页、缺失引用、frontmatter 完整性 |

## 二、适用场景

### 2.1 适合使用 LLM Wiki 的场景

| 场景 | 说明 | 示例 |
|------|------|------|
| **技术培训知识库** | 将培训材料、课程文档系统化管理 | AI 编程培训、新员工技术入职 |
| **技术调研/选型** | 对比多个技术方案，积累调研笔记 | 框架选型、工具链评估 |
| **项目文档中心** | 管理需求、设计、会议纪要等项目文档 | 产品开发过程文档 |
| **读书/学习笔记** | 逐章阅读，构建人物、主题、概念网络 | 技术书籍精读、论文研究 |
| **竞品分析** | 持续跟踪竞品动态，建立结构化对比 | SaaS 产品分析、市场调研 |
| **团队知识沉淀** | 将 Slack、会议、代码评审中的知识系统化 | 团队 Wiki、技术博客素材库 |
| **个人知识管理** | 管理各类笔记、文章收藏、思考记录 | 个人 PKM、Zettelkasten 方法 |

### 2.2 不适合的场景

| 场景 | 原因 | 替代方案 |
|------|------|----------|
| 实时协作文档 | Wiki 由 AI 单人维护，不支持多人同时编辑 | Google Docs、Notion |
| 大规模数据库 | Markdown 文件不适合结构化数据查询 | 数据库 + BI 工具 |
| 需要严格权限控制 | 文件系统级别的权限管理较弱 | Confluence、SharePoint |
| 内容少于 5 个源文件 | 投入产出比不高，直接读源文件即可 | 直接与 AI 对话 |

**步骤 9**：告诉 AI 摄入文件

在 Copilot Chat 中说：

```
请摄入 raw/ 目录下的所有文件
```

或者逐个摄入（推荐，可以参与讨论）：

AI 会自动完成以下步骤：

```

3. 在 wiki/concepts/ 创建或更新概念页
4. 在 wiki/entities/ 创建或更新实体页
```

## 六、常见问题

### Q1：AI 会修改我的源文件吗？

**不会。** `raw/` 目录是只读的，AI 只会读取源文件，绝不修改。所有 AI 的产出都在 `wiki/` 目录中。

### Q2：摄入一个文件需要多长时间？

通常 **1-3 分钟**，取决于源文件的长度和复杂度。一个源文件会触及 5-15 个 Wiki 页面。

### Q3：可以摄入哪些格式的文件？

| 格式 | 支持度 | 说明 |
|------|--------|------|
| `.md` (Markdown) | ✅ 最佳 | 推荐格式 |
| `.txt` (纯文本) | ✅ 良好 | 直接可读 |
| `.pdf` | ⚠️ 部分 | 需要 AI 支持 PDF 解析 |
| 图片 (`.png`/`.jpg`) | ⚠️ 部分 | AI 可以读取图片内容（视觉理解） |

### Q4：知识库变大后会不会变慢？

小型知识库（<50 个源文件，~100 个 Wiki 页面）使用 `index.md` 索引即可。如果规模更大，可以引入搜索工具（如 [qmd](https://github.com/tobi/qmd)）。

### Q5：如何备份知识库？

```
git init
git add .
git commit -m "wiki snapshot"
```

知识库就是一个文件夹里的 Markdown 文件，用 Git 即可完整备份和追踪历史。

### Q6：多人可以共用一个知识库吗？

可以通过 Git 仓库共享，但 **同一时间建议只有一个 AI 会话** 在操作 Wiki，避免冲突。人类可以随时阅读。

### Q7：Schema 配置文件可以修改吗？

可以。`.github/copilot-instructions.md` 是你和 AI 共同迭代的配置文件。你可以随时修改标签体系、实体类型、操作流程等。
